# UX 契约：每块界面都要能回答三个问题

> 背景：v28 修「网络体检」时发现，页面只给了体检结论，没有告诉用户「接下来做什么」。
> 这类问题可能反复出现，所以这里落一条可复用的界面契约，避免同类问题继续出现。

## 1. 三问契约

每个页面、每张状态卡、每个空状态，至少要回答：

1. **这是什么 / 我现在在哪？** —— 标题 + 一句人话说明，不假设用户懂术语。
2. **现在是什么状态？** —— 用「已验证 / 未知 / 不通」这类结论，不用裸指标。
3. **我下一步做什么？** —— 一个明确动作，最好再给一个备用出口。

只做第 2 步、不做第 3 步，产品就停在体检阶段，没有形成闭环。

## 2. 冗余设计

同一个目标至少给两条路：

| 场景 | 主路径 | 备用路径 |
|---|---|---|
| 联机 | 复制可用地址发给朋友 | 开隧道 / 换网络 / 诊断码 |
| 空世界 | 新建世界 | 导入现有数据包 / 修复旧包 |
| 空玩家 | 去联机页拿地址 | 启动服务器 / 配置隧道 |
| 搜索无结果 | 清空搜索 | 换英文名 / 换分类 |
| 配置读不到 | 重试 | 打开目录 / 看日志 |
| 加入失败 | 复制诊断码 | 进服包 / 手动检查客户端 |

冗余指同一目标有不同可行动作；单纯重复文案没有价值。

## 3. 文案规则

新增/改写文案必须遵守：

- 不用「雷霆小短句」堆砌；一个意思写成完整句子。
- 前后逻辑连贯，结论在前，原因和动作在后。
- 不用「不是…是…」「不是…而是…」「并非…而是…」这类否定—转折句式。
- 破折号只用于必要的补充，不拿它连接两个短句。
- 不写「不会动你的文件」「不会锁死」这类此地无银的自我辩解；直接说程序行为。
- 技术名词第一次出现时，用一句人话解释，或者给一个「这是什么」的提示。

## 4. 已按契约检查的页面

| 页面 / 区域 | 这是什么 | 状态 | 下一步 | 结果 |
|---|---|---|---|---|
| 总览 | 当前服务器的运行与联机摘要 | 运行状态 / 朋友能不能进来 | 启动、邀请、联机设置 | ✅ 标题改为「朋友能不能进来」，描述给动作 |
| 实例总览 | 单台服务器的摘要 | 同上 | 邀请、编辑、下一步卡片 | ✅ 邀请卡片有说明与动作 |
| 控制台 | 服务器实时日志 | 空 / 有日志 / 过滤无结果 | 启动、清空过滤 | ✅ 空状态有启动按钮 |
| 配置 | server.properties 表单 | 读到 / 读不到 | 保存、重试 | ✅ 读不到有重试 |
| 内容 | 已装模组/插件 + 资源库 | 空 / 有内容 | 去资源库、打开目录 | ✅ 空状态有动作 |
| 世界 | 自定义维度数据包 + 备份/时间机 | 版本不支持 / 空 / 有包 | 新建、修复、备份、恢复 | ✅ 版本门禁 + 下一步提示 |
| 玩家 | 在线、白名单、OP、封禁 | 空 / 有数据 | 去联机拿地址、启动服务器 | ✅ 空状态补动作 |
| 联机 | 判断朋友能不能进来 | 对称 NAT / 无 IPv6 / 有地址 | 复制地址、走隧道 | ✅ 下一步卡 + IPv6 一键复制 + 兜底按钮 |
| 加入 | 解析邀请并检查客户端 | 有效 / 失败 / 探测中 | 复制地址、进服包、诊断 | ✅ 地址旁复制按钮 |
| 设置 | 外观、运行、同步、关于 | 各分区 | 每张卡有明确开关/按钮 | ✅ 已有说明与动作 |
| 客户端 | 本机 .minecraft | 扫到 / 扫不到 | 选择目录、重新扫描 | ✅ 有动作 |
| 我的服务器 | 收藏的邀请 | 空 / 有记录 | 加入新服务器 / 继续 | ✅ 空状态有动作 |

## 5. 组件约束

- 状态结论 + 动作统一用 `Callout`（`src/renderer/components/ui/callout.tsx`），不要每处手写一套。
- 卡片标题用 `SectionHead` 时必须带 `desc`；没有 `desc` 的卡片要么是纯数据，要么补说明。
- `EmptyState` 必须带 `action`；确实没有动作时，说明为什么没有。
- 地址类文本必须可复制；复制按钮不能只给房间码，直连地址也要给。
- 技术状态旁必须有人话结论，例如「对称 NAT」旁边写「直连基本不通，建议走隧道」。

## 6. 下一轮检查方式

1. 每页截图，按三问逐卡检查。
2. 每个空状态、错误状态、加载状态都点一遍。
3. 对「只有状态没有动作」的卡片，补 `Callout` 或 `EmptyState action`。
4. 新增文案跑一遍第 3 节规则；发现否定—转折句式就重写。
